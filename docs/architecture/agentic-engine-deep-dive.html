PHASE 0
What the engine is (60 seconds)

Istara's "agentic engine" is not one program. It is a dispatch architecture: a thin router (backend/app/core/agentic/dispatcher.py) that sends each turn to one of two execution planes, both of which ultimately call the same provider layer and the same tool executors:

┌─────────────────────────┐ POST /api/chat ────────▶│ AgenticDispatcher │ dispatcher.py:175 │ .chat_turn() │ └────────┬────────────────┘ resolve_engine() │ header → project → global default ┌────────────────┴───────────────┐ ▼ ▼ LEGACY plane PI plane Python ReAct loop Node worker + sessions agentic/legacy.py pi_runtime/engine.py → supervisor.py → worker.mjs │ │ └────────────────┬───────────────┘ ▼ provider call + execute_tool() + usage ledger + telemetry

The core AI-engineering idea: separate thinking in loops from calling models. The loop (how many steps, when to use tools, when to stop) lives in Python or in the Node session driver; the model itself only ever sees "here is the conversation, reply or emit tool calls." Everything else — budgets, secrets, retries, cost caps, audit — wraps around that split. Keep this picture in mind; every phase below zooms into one box.

Teaching lens: this is the classic ReAct pattern (Reason + Act, Yao et al. 2022): thought → action → observation → thought… until done. Istara runs two ReAct implementations — one in Python (legacy, tool loop owned locally), one in Node (Pi, tool loop owned by the worker session) — behind one router, so behavior, budgets, and receipts stay comparable.

PHASE 1
Entry: POST /api/chat

File: backend/app/api/routes/chat.py, function chat() at line 907. A chat turn is a Server-Sent Events stream, not a single JSON reply, so tokens, tool calls, and usage frames arrive incrementally. The handler does eleven things before any model is touched:

  1. Authorize the project (:913) — get_visible_project_or_404. No project access, no turn. Multi-tenancy starts here.
  2. Bind an optional task (:924) — a turn may belong to a Kanban task, but only inside the same project (causal lineage for the usage ledger).
  3. Resolve the engine (:940) — header x-istara-agent-engine → project setting → global default (legacy). Same precedence the UI advertises.
  4. Resolve or create the chat session (:965) — sessions carry model_override, endpoint_override, thinking_mode, inference presets. This is why an old session can show a different model than a new one: the choice is persisted per session.
  5. Persist the user message first (:990) — the turn is on record even if generation later fails.
  6. Load session inference settings (:1020) — temperature, max tokens, model/endpoint overrides, effort.
  7. Compose the agent identity (:1060/1088) — compose_dynamic_prompt (Prompt-RAG: retrieves only the persona sections relevant to this query, not whole files).
  8. Retrieve RAG context (:1098) — hybrid vector + keyword search over the project's stores.
  9. Budget + compress (:1107) — budget_coordinator and compress_rag_chunks fit retrieval into the context window.
  10. Assemble history (:1171) — prior turns, then context_summarizer + ContextWindowGuard (:1190) keep it inside limits (old turns get summarized, not silently dropped).
  11. Prepend system + thinking control (:1228) — then enter generate() (:1231).

Inside generate() the route picks a generator. This is the most important branch in the chat path:

# chat.py — which generator runs your message?
if pi_candidate_available:          # :1259 — Pi endpoint resolved?
    yield from _generate_pi_runtime(..., max_turns=PI_MODEL_TURN_BUDGET)  # :1282, budget = 24
else:
    yield from _generate_native_tools(..., max_turns=MAX_TOOL_ITERATIONS)   # :1299, budget = 8
# fallbacks: :1312 bad-request/tool-unsupported/no-compute → :1358 _generate_text_fallback
# every path ends at :1390 persist + :1432 done{sources, tools_used}
Note the asymmetry: Pi chat gets 24 model turns (PI_MODEL_TURN_BUDGET = MAX_TOOL_ITERATIONS * 3, chat.py:84–90), legacy chat gets 8 tool iterations (:690). Same question, different stamina, depending on the engine chip in the toolbar.

PHASE 3
The dispatcher: one door, two planes

File: backend/app/core/agentic/dispatcher.py. Every agentic verb — chat_turn (:175), completion (:272), structured (:345), react (:425), ensemble (:515), embed (:611) — flows through engine resolution (:118–172) with this precedence:

  1. Per-call engine= argument (benchmarks, A2A).
  2. Request header x-istara-agent-engine (only the values in PI_ENGINE_VALUES select Pi; anything else → legacy).
  3. The project's agentic_engine (read-only DB lookup).
  4. Global default agentic_engine_default = "legacy" (config.py:427).

Then: Pi → _collect_pi_stream over _pi.run_chat_turn; legacy → _legacy_outcome into legacy_executor. There is no silent fallback — an exception records a failure row and re-raises (:716–745). A turn that cannot run fails loudly as a typed error, never as a confident hallucination. That fail-closed reflex is the spine philosophy in one habit.

PHASE 4
The legacy ReAct loop, line by line

File: backend/app/core/agentic/legacy.py, _react_loop at line 271. This is the clearest ReAct implementation in the repo — the whole loop fits in ~220 lines. Annotated pseudocode (line numbers are real):

# legacy.py — the loop that thinks in turns
budget = params.max_turns or 8              # :284-288  (chat passes 8, skill tasks pass 5)
history = messages + [user_text]            # :296-299

for iteration in range(budget + 1):             # :357 — note the +1: 9 provider calls max
    outcome = await run_provider_turn(       # :363 — the ONLY model call; tools=None in
        system, history,                       #     text-fallback mode (:369)
        tools=tools, stream_cb=...)            # stream only when native tools (:371)
    if outcome.status != "success": raise AgenticDispatchError  # :373 — fail, don't improvise
    message = {assistant, content, tool_calls} # :380-388

    # --- PATH A: text fallback (models without function calling) ---
    if text_fallback:                       # :390 — regex-extract {"tool":..} blocks
        call, before, _ = extractor(turn_text)  # :391 (_TOOL_CALL_BLOCK_RE :236)
        if call and iteration < budget:
            result = await tool_executor(name, args, project, agent)  # :402
            history += assistant:"[Tool:name]"            # :407 — observation re-enters
            history += user:"[Tool result:name]:\n{result}\n\n{followup}"  # :417
            continue
        return _outcome(stop or turn_budget_exceeded)  # :428-435

    # --- PATH B: native function calling ---
    raw_calls = filter(hallucinated_names, allowed_names)  # :441-456 — a model that
                                                     # invents tools gets filtered, mined for
                                                     # text, and carries on
    if not raw_calls or iteration >= budget or executor is None:  # :458
        return _outcome(stop if quiet else turn_budget_exceeded)  # :466
    history += message                       # :474 — assistant turn re-enters
    for call in raw_calls:                # :475 — SEQUENTIAL, one at a time
        result = await tool_executor(...)        # :479
        history += {role:tool, id, name, content}  # :480-487 — observation re-enters
raise AssertionError  # :488 — provably unreachable; the loop always returns

Three design decisions to notice:

  • Observations re-enter as history. Tool results are appended as tool (or user in fallback) messages, so the next provider call literally reads its own notes. That append-only conversation is the agent's working memory.
  • Hallucinated tools are filtered, not fatal. A model inventing a tool name gets that call dropped and its text mined — robustness over purity.
  • The loop always terminates with a named reason — stop vs turn_budget_exceeded. Callers (and telemetry) can tell "done" from "ran out of steps."
Teaching lens — the stopping rule is the whole ballgame. Line 458 is where "answers too fast" lives: the first iteration with zero tool calls returns immediately. There is no planner, no critic, no "are you sure?" pass. One ReAct pass, then done.

PHASE 5
The Pi plane: supervisor, worker, sessions

Files: backend/app/core/pi_runtime/engine.py (Python side), supervisor.py (process owner), pi-runtime/src/worker.mjs + session.mjs (Node side). Where legacy keeps the loop in Python and calls the model per step, Pi moves the loop into a long-lived Node child process and speaks to it over versioned NDJSON frames on stdin/stdout (supervisor.py:1–12).

PHASE 6
Tools: catalog, execution, idempotency, audit

Both planes call the same tools through execute_tool() (backend/app/skills/system_actions.py). The pipeline around every call:

  1. Catalog admission — the worker only sees the tools in its session catalog; the Python handler re-checks membership and rejects out-of-catalog calls with a tool_not_allowed audit row (engine.py:297–322). The model cannot talk itself into new powers.
  2. Project/agent re-injection — the handler stamps the current project_id / agent_id server-side. Tool calls are always executed as someone, somewhere.
  3. Idempotent execution — execute_with_idempotency ( engine.py:310–321) so retried frames don't double-apply mutations.
  4. Canonical telemetry span — every call records operation="tool_call" with name, duration, success, model, agent, task (telemetry.py:record_tool_call). This is what powers the Tool Audit Trail, per-model reliability stats, and the security benchmark's tool-visibility controls.
  5. Content-free summaries — the audit trail stores parameter names, never values; lesson links are opaque IDs. Observability without surveillance.

Fixed tool subsets scope special verbs: delegation, channel, and autoresearch turns each get a narrowed catalog (engine.py:62–100) — least privilege per mission type.

PHASE 7
Secrets: how credentials never leak

At rest: OAuth blobs are Fernet-encrypted in the DB; API keys live in env first, then macOS Keychain (config.py:159–183); a 60 s TTL cache bounds Keychain reads (endpoints.py:29).
In flight: secrets cross exactly one boundary — the local stdin pipe inside provider.bind — into per-session PI_RUNTIME_KEY_N env vars that are deleted on dispose (provider.mjs). Worker logs are secret-free by construction; telemetry carries endpoint identities (ids, hashed account handles), never keys.

Model resolution itself (model_manager.resolve) is an admission predicate, not a search: endpoint id, model name, min context, vision need, project scope — anything unmatched fails closed (unknown / model_mismatch / no_matching / insufficient_distinct). Single-endpoint setups honestly report not_runnable for ensemble methods instead of faking multi-model consensus.

PHASE 8
Money and memory: usage ledger + telemetry

Exactly one AgenticUsageRow per dispatch (usage_ledger.py:279–341): model served, latency, tool count, turns, exact-vs-estimated usage, error type — plus an identity span. Exactness rules are strict: Pi needs every sample receipt; legacy accumulates all-or-nothing; anything else is labeled estimate or zeroed. Research-spine telemetry (coding runs, reliability, reconciliation, retrieval modes, donor lifecycle) rides the same span bus as content-free handles — which is why the Quality and Ensemble dashboards can show per-model truth without ever storing a prompt.

PHASE 9
Why answers feel fast (the budget autopsy)

Your observation is correct, and it is structural, not a bug. Count what one complex question gets:

SurfaceSteps grantedPlans?Critic?Continues?
Chat, legacy engine8 tool iterations (9 provider calls)NoNoNo
Chat, Pi engine24 model turnsNoNoNo
Skill task5 iterations + 600 s + 120 s validationNoYes — validation methodsNo

Five compounding reasons for speed:

  1. Single ReAct pass. One loop per turn, no decomposition into subgoals. A 6-part question gets the same machinery as "what time is it".
  2. First-quiet-turn wins. The moment the model replies with no tool call, the loop returns (legacy.py:458). There is no "sleep on it" pass.
  3. Sequential tools. Independent calls run one at a time (:475); wall-clock pressure discourages broad evidence gathering.
  4. No cross-turn plan state. Sessions persist overrides and history, but nothing records "step 2 of 5, hypothesis X pending" — each turn re-derives intent from scratch.
  5. Validation exists — but beside the loop, not inside it. Adversarial review, debate, ensembles all run as post-hoc task validation, never as mid-chat self-correction.
The good news: every prerequisite for longer horizons already exists — sessions with revisions, steering mid-run, usage/cost accounting, validation methods, task promotion, compaction. The engine needs orchestration between its parts, not new parts.

PHASE 10
Long-horizon upgrade plan (12 proposals)

Constraints honored throughout: fail-closed errors, project scoping, content-free telemetry, provider/model authority in Pi Model Management, no silent fallbacks. Ordered by leverage. Proposals 1–8 came from the code study; 9–12 were added with the literature and live-measurement research in Appendix A/B. Each names the repo seam it reuses — nothing here needs new machinery, only orchestration between existing parts.

1. Budget-aware continuation highest leverage · small

Surface stop_reason in the UI ("used 8 of 8 steps — keep going?"). A Continue re-opens the same session revision with the accumulated history, granting a fresh budget. Implementation: one button + one route param; the worker already supports rehydrate (session.open revision, worker.mjs:143–150). Turns a cliff into a ramp.

2. Plan-then-execute for complex questions high leverage · medium

A lightweight planner pass (structured output: subgoals with tool hints) runs first for questions classified complex; each subgoal executes as a chained turn in the same session; a final synthesis turn answers. State = an append-only plan ledger (mirrors the existing usage ledger pattern). Spine gates stay: subgoals are provisional until the normal validation passes.

3. Mid-run critic high leverage · medium

Move one existing validation method inside long runs: after N tool observations, run a validation.judge pass (already built for adversarial review) asking "is this on track? what's missing?" — feed the verdict back as an observation. No new models, no new prompts family.

4. Parallel tool fan-out medium · small

Independent calls (search ×3, fetch ×2) dispatch concurrently with a barrier join — the same fan-out/barrier discipline the repo's own multi-agent orchestration uses. Wall-clock per evidence unit drops; budgets buy breadth instead of waiting.

5. Explicit plan state in sessions medium · medium

Extend the session revision payload with plan: {goal, steps[], done[], open_questions[]}, compacted alongside history. Stops the "re-derive intent every turn" tax and makes steering surgical ("redo step 3").

6. Promote-to-task bridge medium · small

Chat already binds turns to tasks (chat.py:924). Offer "keep working on this as a task" when a turn exhausts budget: the 600 s / validation-equipped task machinery takes over, and results stream back to the chat. Uses existing rails end to end.

7. Budget escalation UX medium · small

Show live budget (steps, wall-clock, spend vs the $1.00 cap) in the chat chrome, with per-question budget selection. Users who want depth opt into it; default stays snappy.

8. Ensemble spot-checks on hard answers lower · medium

For high-stakes or low-confidence answers, run a second model pass and show agreement — resolve_distinct already fails closed on single-endpoint setups, so this degrades honestly where it can't run.

9. Complexity-routed effort tiers high leverage · small

Classify the question before spending: trivial → today's budgets; complex → escalated turn/time/cost caps with the planner engaged. Evidence E1 is the smoking gun — a 3-part question consumed 3 of 24 turns while a one-liner gets the same ceiling; fixed budgets starve the hard and indulge the trivial equally. Routing rule lives beside engine resolution (dispatcher.py:118–172), tiers reuse existing TurnParams.max_turns and the $1.00 cost cap, and the tier label joins the usage row so spend stays auditable. Why it is safe: it only selects budgets that already exist; the fail-closed machinery is untouched. Literature: adaptive-compute / complexity routing — spend inference where uncertainty is highest.

10. ReWOO-style decoupled planner high leverage · medium

One planner call emits the entire tool-call plan upfront (steps + which tool + with what arguments); plain executors then run it with zero per-step LLM calls, substituting variables as evidence arrives. On evidence-heavy questions this collapses a 12-call ReAct trace into ~2 model calls with identical tool coverage — cheaper, faster, and more predictable than looping. Seams: the tool catalog + execute_with_idempotency (engine.py:310–321) already support exactly this shape, and the forced emit_structured_output capture (engine.py:742) is the plan-envelope format waiting to happen. Guardrail: the plan itself is validated like any structured output, and every step still executes through the audited execute_tool front door. Literature: ReWOO (decoupling reasoning from observations).

11. Persistent plan memory with compaction guard medium · medium

Extend the session revision payload (the structure the worker already rehydrates, worker.mjs:143–150) with plan: {goal, steps[], done[], open_questions[], hypotheses[]}, compacted alongside history by the existing summarizer — with the same protected-block treatment the prompt compressor already gives protocol/codebook spans, so compaction can never summarize the plan away. This ends the "re-derive intent every turn" tax measured in Phase 9 and makes steering surgical ("redo step 3", "drop hypothesis B"). Telemetry stays content-free: plan counts and statuses, never plan text.

12. Depth eval harness: today's probe, automated enabler · small

Turn Evidence E1 into a standing scenario suite: multi-part tool questions with asserted expectations on turns-used, tools-used, subgoal coverage, and terminal reason (must be stop with all parts answered, or a typed budget frame — never a quiet partial). Run pre/post on every engine-affecting change next to the accepted benchmark bundle (comparison-Istara-pi/…/scorecard.json), whose verdict (no_significant_difference: Tool Calling pi 0.8077 vs legacy 0.8312; Quality 6.75 vs 6.6364) is the parity bar no proposal may regress. This is how "works longer" becomes a number instead of a feeling. Literature: the SWE-bench / τ-bench / BFCL ethos — task-success harnesses, not vibes; deterministic industry scores already feed the bundle's first axis.

What NOT to do: raise the raw budgets alone (more steps ≠ deeper thought — single-pass ReAct just wanders longer); add an unlogged shadow planner (breaks the evidence chain); let the worker fetch tools outside its catalog (breaks least privilege); mix vector spaces across engines (breaks the embedding invariant).
