## 2. Directly reusable vs must-build for paired Pi-vs-legacy runs

**Reusable as-is**
- `metrics-schema.json` v3 (<repo-root>/comparison-Istara-pi/metrics-schema.json) — the target per-run record: `run.engine: istara|pi`, 10-phase step trace with per-step tokens/tool validity/memory/a2a/quality/failure_category (`:69-109`), roll-ups `quality_per_1000_tokens`, `quality_per_tool_call`, `marginal_tool_gain` (`:117-119`), `statistics.paired_delta` + bootstrap CI (`:121-126`).
- `x-istara-agent-engine` header switch (`tests/real_user_benchmark/lib/api-client.mjs:31,244`) — per-request engine routing for any HTTP-driving harness.
- Deterministic checkers in `run_istara_evals.py:308-377` (json/dag/field checks) — engine-agnostic on final text; live cases in `core_eval_cases.json` runnable against either engine.
- Run-manifest hygiene: git sha + dirty flag + input sha256 + secret sanitization + `.results`-only output guard (`run_istara_evals.py:90-134,161-179`).
- Lab paired-runner skeleton: `IstaraContractBaseline` vs `IstaraPiAdapter` run over the same scenario catalog with shared facade + summarizer (`collect-replacement-artifacts.mjs:518-543`); raw-capture module (`raw-llm-capture.mjs`) incl. usage normalization + cost estimation + append/dedupe gzip JSONL; spend-ledger pattern (`:663-668`).
- 78 simulation scenarios as behavioral fixtures (each returns structured `checks[]`); real_user scorecard rubric + fail-closed research-spine gates; `fleiss_kappa` prod function for A2A agreement.
- Per-feature criteria source: `docs/features/inventory.json` (65KB; per feature `id`, `ui_path`, `nav_group`, `code_refs`, `store_refs`, `api_refs`, `test_refs`, `related_features`, `status`). `scripts/feature_docs.py` reads `docs/features/{inventory.json, content/, glossary/, site-design.md}` and generates `docs/features/site/` static HTML — the inventory is the machine-readable spine from which `feature_success.criteria_scores` (reachable/project_scoped/expected_action/engine_behavior/evidence_emitted/graceful_failure) can be derived.
- `tests/agentic_eval_contract.json` — named eval_metrics per feature area, reusable as the axis→metric vocabulary.

**Must be built**
1. Real Istara service adapters behind the canonical tool facade (explicit `blocked_on`, evaluation-lab-plan.md:10) — lab tools are in-memory envelopes; nothing writes to DB-backed tasks/documents/memory/skills/A2A/channels.
2. A paired runner emitting metrics-schema records: nothing today computes `paired_delta`/bootstrap CI, `quality_per_1000_tokens`, or `marginal_tool_gain`.
3. Per-step token accounting for the LEGACY engine: `long_horizon_runner.py:138` counts SSE chunks as "tokens"; simulation/real_user harnesses don't capture usage. Requires tapping backend telemetry (`telemetry_tokens_tool_metrics` surface) or SSE usage events.
4. Engine-flag plumbing: `run.mjs` (both simulation and real_user) has no engine parameter; simulation scenarios drive UI/`/api/chat` without the header.
5. Live research-spine per-step scorer: lab `quality_score`s are self-declared inside faux tool args (`scenario-catalog.mjs:357,367,374,383`); real_user spine probes verify process gates, not per-step quality grading.
6. LLM JudgeLayer (planned only, evaluation-lab-plan.md:338-341); all current quality signals are boolean proxies.
7. Memory-load instrumentation per step (memory_items/memory_tokens/scope in schema `:96-98`; lab records only counts of in-memory records, `collect-replacement-artifacts.mjs:604-614`).
8. Per-feature criteria compiler: inventory.json → feature_success assertions (no assertions exist in inventory; `test_refs` mostly empty for shell features).
